# G428-M3 off-host join window — pre-registered protocol

**Status: DRAFT — NOT EXECUTED.** This runbook fixes the protocol before a run so the result cannot
be chosen after the fact. It does not claim that any run has happened.

- Gate: `G428-M3` — off-host bootstrap and fringe completion (`spec/audit/mainnet-gates.json`).
- Owner: Aria / evidence work. Operator and independent reviewer to be named before the window.
- Evidence destination: `spec/audit/evidence/m3-offhost-<date>/`.
- Prerequisite reading: `spec/audit/evidence/m3-m5-pareto-20261101/M3-14-journal.md` (the six stages
  and the keying rule) and `spec/audit/runbooks/n487-live-postdeployment-20261108.md` (the evidence
  shape this runbook reuses).

## 1. What this window must establish

An external observer advertises a **routable** peer address, authenticates and joins, receives and
applies the approved fringe, and hydrates state. The witness is the typed six-stage chain produced
by `tools/m3-join-chain.py`:

| stage | source | required content |
|---|---|---|
| 1 request | joiner | responder peer key and requested anchor |
| 2 receipt | responder | joiner's full advertised `rnode://` address and requested anchor |
| 3 construction | responder | served state hash, requested anchor, block count and range |
| 4 transport | responder | `transport outcome delivered` (not a send line) and the served hash |
| 5 receive | joiner | served state hash, blocks, responder peer key |
| 6 apply | joiner | served = received = restored = walked hash; page walk finished; checkpoint read back |

Stage 4 is the joiner's gRPC receiver acknowledgement, not handler completion. Stage 6 records the
certificate's accepted run root separately; for a certified fringe it is not the served fringe
hash, and the chain requires equality only for a genesis anchor.

The chain also names its raw logs (`logs.joiner`, `logs.responder`). Every quoted `log_line` must
appear verbatim in the named file; `check --record` enforces that, and an off-host record must also
cover both files in `SHA256SUMS.json`. The chain's `complete` must be `true` with an empty
`incomplete_reasons`, and stage 4's words and outcome must agree (`sent to` ⇒ `delivered`,
`was not sent` ⇒ `failed`).

## 2. Hard NO-GO conditions

- Fewer than two independent hosts, or a shared Docker bridge. The observer must advertise an
  address the bootstrap can dial that is not loopback, private, link-local, reserved or a
  legacy-numeric form.
- No captured dial-back result from the bootstrap to the observer's advertised address.
- A chain that is absent, incomplete, keyed only by a send line, or whose served and restored hashes
  differ.
- A chain whose quoted lines are not present in the named raw logs, or (for an off-host record)
  whose raw logs are not digest-pinned by `SHA256SUMS.json`.
- A local-devnet or single-host record submitted as an off-host claim.
- Any gate promotion is out of scope: none is expected from this run.

## 4. Procedure

1. On host A, start the bootstrap with the selected binary and the pre-registered genesis/chain.
2. On host B, start the observer with `--bootstrap <A-address>`; record the observer's peer key and
   its advertised address. The observer is an external node, not a validator introduced into A's
   committee.
3. From A, dial the observer's advertised address and capture `raw/dial-back.txt`. The join is not
   started before this succeeds.
4. Let the observer join. Capture `raw/bootstrap.log` on A and `raw/observer.log` on B without
   filtering; the correlation reads the lines, not a hand-written summary.
5. Build the chain:
   ```sh
   python3 tools/m3-join-chain.py build \
     --joiner-log raw/observer.log --responder-log raw/bootstrap.log \
     --joiner-container observer --responder-container bootstrap \
     --joiner-source raw/observer.log --responder-source raw/bootstrap.log \
     --locality off-host-claim --out <run-dir>/chain.json
   ```
   `evidence-pack.py` copies the run directory under `raw/`, so the checker reads
   `chain.json` at the record root or under `raw/`. The build records the inputs' basenames
   (`observer.log`, `bootstrap.log`); keep both files in the run directory so the packer copies
   them and the checker can bind every quoted line to them. `joiner` and `responder` must name
   distinct files, and a packed record pins the selected `chain.json` in `manifest.json` as
   `kind: json` with a matching `sha256` and byte count, and in `SHA256SUMS.json`.
   Off-host admission also pins the two source logs: both `--joiner-source` and `--responder-source`
   are record-relative after packing, and the packed record must list both in `manifest.json`
   (kind `log`) and `SHA256SUMS.json` with matching digests and byte counts. Every quoted stage
   line must appear in the correct pinned source, and the completed page-walk line in the joiner's.
   Absent or mismatched source pins refuse off-host admission. Older local-devnet records without
   responder logs remain diagnostics and must never be upgraded or retrospectively reconstructed.
6. Check it:
   ```sh
   python3 tools/m3-join-chain.py check --record <record> --locality off-host
   python3 tools/gate-check.py --gate G428-M3 --observations <record>/observations.json
   ```
   `observations.json` is `{"record": {"dir": "<record path>"}}`. A `PRECONDITION` means a stage
   could not be keyed: record it as INCOMPLETE, never repair it by re-running the join to
   manufacture the stage.
7. Pack and verify:
   ```sh
   python3 tools/evidence-pack.py pack --run-dir raw --record <record> \
     --gate-id G428-M3 --verdict INCONCLUSIVE --locality off-host-claim \
     --source-sha <40hex> --binary-sha256 <64hex>
   python3 tools/evidence-pack.py verify --record <record> --require-pins
   python3 tools/check-evidence-locality.py --gate
   ```

## 5. Negative controls (each recorded in the same window or in a separate labelled record)

- **Loopback advertised from B.** Point the observer's advertised address at `127.0.0.1` and require
  the bootstrap to refuse it clearly; `check --locality off-host` must FAIL the resulting record.
- **Send-log-only.** Remove stage 4 from the chain; `check-chain` must FAIL.
- **Served ≠ restored.** Change `6_apply/restored_state_hash`; `check-chain` must FAIL.
- **Unkeyed chain.** Replace stage 2 with a send line; `check-chain` must FAIL.

A negative control is evidence only in a record that carries it; do not describe a control that was
not captured.

## 6. What this window does not establish

- It is not failover (M3-11) and does not exercise an alternative peer.
- It is not a proof that the run happened: `execution_proven` is false; the digests prove the bytes.
- It does not promote `G428-M3`; the register's witness/control/evidence binding is a separate
  decision after the record is reviewed.
- It makes no claim about the supported resource tier or about a public network's safety.
